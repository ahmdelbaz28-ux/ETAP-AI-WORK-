# مراحل الإغلاق — دليل الاستخدام (للمستشار والمنفذ)

## كيف تُستخدم هذه الملفات

1. أرسل **ملف مرحلة واحد فقط** للوكيل المنفذ — ممنوع إرسال أكثر من مرحلة في جلسة واحدة.
2. الوكيل لا يقرأ ملفات المراحل الأخرى ولا وثيقة البرومبت الأصلية (منعًا لفقدان السياق والتشويش).
3. في نهاية كل مرحلة: الوكيل يكتب تقريره بنموذج `docs/status/REPORT_TEMPLATE.md` ويحدّث `docs/status/STATUS_BOARD.md` ثم **يتوقف**.
4. المستشار (أنا) يراجع الأدلة، يصحح المسار إن لزم، ثم **يصرّح** ببدء المرحلة التالية.

## الترتيب الملزم

```
S0 التثبيت وخط الأساس
 → S1 إغلاق BYOK الصدق (CORS/توثيق/اختبارات)
 → S1.5 إغلاق F-BASE-A (8 إخفاقات خط أساس حقيقية: قوس×2 · rate-limit×3 · HF-parity×1 · symlink×1 · headers×1)
 → S2 إغلاق IEC 60909 (Method + توثيق البنود)
 → S3 تدقيق أدلة الثقة (لا رقم بلا أمر)
 → S4 الطوارئ الحقيقي + Stop لكل عملية
 → S5 وكيل التصميم (إكمال/عزل) + إصلاح dispatch
 → S6 القياس النهائي الشامل (تجميد كامل)
 → S7 الدفع النظيف (فرع → PR → CI → Squash)
 → S8 التقرير النهائي + HF smoke
```

## الثوابت غير القابلة للتفاوض

- **لا force-push** على `main` أو أي فرع مشترك. لا دفع مباشر إلى `main` بعد S0.
- **لا ادعاء بلا أمر**: كل رقم في أي تقرير له أمر نُفِّذ ونتيجة حرفية.
- **لا بيانات وهمية/fallback** في أي شاشة أو تقرير (الصدق > الجمال).
- **لا تعديل خارج قائمة الملفات** المصرح بها في ملف المرحلة؛ أي خروج يُبلَّغ **قبل** التنفيذ ويُوثَّق.
- **لا تجاوز** `tool_policy` أو نظام الموافقات أو أي بوابة CI حمراء.
- **التجميد أثناء القياس**: ممنوع تعديل ملف واحد أثناء تشغيل الاختبارات؛ يُثبت بثبات `git rev-parse HEAD` قبل/بعد.
- أي بند لا يُنفَّذ: يُكتب «غير منفذ + السبب + اقتراح الجولة القادمة».
