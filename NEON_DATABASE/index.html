    Connection Strings

    The password is stored ONLY as a HuggingFace Space secret. It is NOT committed to the repository. If you need to rotate it, see Rotation below.

    Production (used by HuggingFace ETAP Space)

    postgresql://etap_owner:<PASSWORD>@ep-restless-surf-atp743eu.c-9.us-east-1.aws.neon.tech/etap?sslmode=require

    This is the direct (non-pooled) endpoint — chosen because: 1. It resolves to IPv4 (52.45.105.76) — required by the deployment target. 2. The ETAP Docker container runs a single uvicorn worker, so connection pooling is handled by SQLAlchemy's queue pool, not PgBouncer. 3. Lower latency than the pooled variant (no extra hop).

    Serverless / Alternative (pooled)

    Use this variant only if deploying to a serverless platform that rapidly recycles connections (e.g. Vercel Functions, AWS Lambda):

    postgresql://etap_owner:<PASSWORD>@ep-restless-surf-atp743eu-pooler.c-9.us-east-1.aws.neon.tech/etap?sslmode=require

    Deployment Wiring

    HuggingFace Space (production)

    DATABASE_URL is registered as a Space secret (not a variable) on ahmdelbaz28/ETAP. The Dockerfile intentionally does NOT set DATABASE_URL — it reads it from the HF secret at runtime.

    To update the secret:

    # Use the HF API (requires a token with write scope on the Space)
curl -X POST \
  -H "Authorization: Bearer $HF_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"key":"DATABASE_URL","value":"postgresql://..."}' \
  https://huggingface.co/api/spaces/ahmdelbaz28/ETAP/secrets

    Or via the web UI: https://huggingface.co/spaces/ahmdelbaz28/ETAP/settings

    Local Development

    Local dev defaults to SQLite (see env.example.txt):

    DATABASE_URL=sqlite:///./db/digital_twin.db

    To test against Neon locally, override DATABASE_URL in your shell:

    export DATABASE_URL="postgresql://etap_owner:<PASSWORD>@ep-restless-surf-atp743eu.c-9.us-east-1.aws.neon.tech/etap?sslmode=require"
alembic upgrade head      # apply migrations
uvicorn backend.app:app --reload   # start backend

    Migrations

    The repo uses Alembic. Migration scripts live under alembic/versions/. To apply migrations to the Neon database:

    export DATABASE_URL="postgresql://etap_owner:<PASSWORD>@ep-restless-surf-atp743eu.c-9.us-east-1.aws.neon.tech/etap?sslmode=require"
cd /path/to/revit
alembic upgrade head

    To check current revision:

    alembic current

    Rotation

    If the etap_owner password is compromised:

    # 1. Rotate via Neon API (returns the new password)
curl -X PUT \
  -H "Authorization: Bearer $NEON_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"role":{"name":"etap_owner"}}' \
  https://console.neon.tech/api/v2/projects/divine-bar-17848047/branches/br-round-mode-at9cfb4a/roles/etap_owner

# 2. Build the new DATABASE_URL with the new password.

# 3. Update the HF Space secret:
curl -X POST \
  -H "Authorization: Bearer $HF_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"key":"DATABASE_URL","value":"postgresql://...new_password..."}' \
  https://huggingface.co/api/spaces/ahmdelbaz28/ETAP/secrets

# 4. The HF Space rebuilds automatically.

    Verification

    To verify the connection works:

    psql "postgresql://etap_owner:<PASSWORD>@ep-restless-surf-atp743eu.c-9.us-east-1.aws.neon.tech/etap?sslmode=require" \
  -c "SELECT version(), current_database(), inet_server_addr()::text;"

    Expected output:

                                  version                               | current_database | inet_server_addr
--------------------------------------------------------------------+------------------+------------------
 PostgreSQL 18.4 on aarch64-unknown-linux-gnu ...                  | etap         | 169.254.254.254

    The 169.254.254.254 link-local address is Neon's internal proxy IP — it confirms the connection is being routed through Neon's IPv4 proxy.
